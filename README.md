```java

    public void rentVehicle(String id, Date d1, Date d2) {
```

**✅ What I do:**
```java
// Good: Loose coupling, testable, maintainable
public class RentalAgency {
    public void rentVehicle(String rentalId, String vehicleId, LocalDate start, LocalDate end) {
        validateVehicleExists(vehicleId);      // Separate concern
        validateCustomerExists(customerId);    // Separate concern
        validateAvailability(vehicleId);       // Separate concern
        
        RentalRecord record = new RentalRecord(...);  // Single responsibility
        rentals.add(record);
    }
}
```

**Key Differences:**
- Validation is explicit (not hidden in spaghetti logic)
- Each method does ONE thing
- Easy to unit test each part
- New business rules don't break old code
- Other developers understand immediately

## 💭 Engineering Philosophy

> **"Smart people write code that works. Great engineers write code that's easy to understand, modify, and extend."**

My core beliefs:

### 1. **Code is Communication**
Code must be readable first, clever second. A developer reading your code 6 months later (possibly you!) should understand it without a PhD.

```java
// Clear intent
if (rentalDate.isBefore(today)) {
    throw new InvalidRentalDateException("Cannot book in the past");
}

// Not this
if (rd < t) throw new Exception("Date error");
```

### 2. **Design Today for Changes Tomorrow**
Most "legacy code" problems come from tight coupling and hardcoded logic. Use patterns not to over-engineer, but to **protect against reasonable future changes**.

```java
// Strategy Pattern in E-Commerce System
// Adding new payment method: 1 new class, 0 existing changes
class CryptoCurrencyPayment implements PaymentStrategy { ... }

// Vs. the alternative:
if (type == "card") { ... }
else if (type == "upi") { ... }
else if (type == "crypto") { ... }  // Now every switch statement is broken
```

### 3. **Testable Code is Good Code**
Code that's hard to test usually has tight coupling, unclear responsibilities, or hidden dependencies. If code is hard to test, it's probably hard to maintain.

### 4. **Learn the Rules Before Breaking Them**
SOLID principles, design patterns, and OOP concepts aren't arbitrary — they're battle-tested solutions to real problems. Master them first, then optimize.
